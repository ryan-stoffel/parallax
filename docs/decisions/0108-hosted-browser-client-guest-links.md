# 0108: A hosted browser client runs plxd's TLS in WebAssembly, and a guest link shows one thread

- Status: accepted, with two calls left to Ryan (below). Amends [0068](0068-relay.md)'s Identity section, its line on web clients, and its Consequences, and [0091](0091-connect-over-relay.md)'s read-only amendment (PLX-1364). Replaces [0065](0065-remote-reach.md)'s line that a hosted copy of the web client lives on the relay's domain
- Date: 2026-11-22
- Issue: PLX-1607

## Context

On 2026-11-22 Ryan brought two things into scope that were out of it: a hosted browser client, as T3 has `app.t3.codes`, and expiring guest access to one thread, as T3 has guest links. T3's guest link shares one thread with one browser for 24 hours, and each message the guest sends waits until the owner sends or dismisses it ([T3 guest links](https://github.com/pingdotgg/t3code/blob/main/docs/user/guest-links.md)).

Parallax's rule is that end-to-end encryption, host-key pinning, and the relay's connect limiter are never weakened. Today every client runs TLS 1.3 to plxd's own P-256 key inside the relay's stream, pinned to the host id (the key's JWK thumbprint), so the relay carries ciphertext only ([0068](0068-relay.md), [0091](0091-connect-over-relay.md)). The phone does this natively (`apps/mobile/modules/pinned-tls`). A browser can't: its own TLS checks a certificate against public roots and offers no pin, and its WebSocket can't carry a TLS session it runs itself.

0068 already named the catch: a web client is end to end only when its JavaScript comes from somewhere the relay's operator doesn't control. Code served from an origin can read whatever it decrypts.

The relay's gates today (`relay/src/index.ts`, `host.ts`): every stream open first passes Cloudflare's rate limit binding, 120 a minute per address (an IPv6 /64) and host, before any object runs. Then the host's object requires a Clerk token for the host's own user, and counts 30 opens a minute per host, at most 16 open streams, and 2 GiB a day, past which it closes every stream until 00:00 UTC. This record calls all of that the connect limiter. Until now only the host's own user, or plxd itself (PLX-1356), could open a stream, and that stream reaches every route of plxd's listener (`daemon/src/server/remote.rs`): the descriptor, pairing, sign-in, webhooks, and `/ws`.

## Decision

### TLS in the browser: rustls compiled to WebAssembly

The hosted client runs rustls 0.23 with ring, the same library and version plxd and `plxd dial` use, compiled to `wasm32-unknown-unknown` through wasm-bindgen. JavaScript feeds it the relay WebSocket's binary frames and takes its records back. It speaks TLS 1.3 only and checks the certificate with plxd's own pin code (`key_id` in `daemon/src/remote.rs`), shared rather than copied: the JWK thumbprint of the certificate's P-256 key must equal the host id, and nothing is sent before it does. It keeps ring's default provider, as plxd's listener does (`remote::provider`), so both prefer AES-256-GCM. Inside the TLS, the client writes its own HTTP, so the `/ws` upgrade carries its DPoP proof and may use `plxd-early-ws`, as `plxd dial` does (0091). Session tickets stay in memory for the page's life, per pin, so a reconnect within an hour resumes with 0-RTT on 0091's terms (PLX-1585), and nothing is kept across reloads.

Measured for this record on the Mac mini (Apple M6) with rustls 0.23.46, ring 0.17.14, wasm-bindgen 0.2.100, `opt-level = "s"`, LTO, and no `wasm-opt`:

| | Result |
| --- | --- |
| Client module with the pin check and ring's default provider | 459 KB, 186 KB gzipped, 150 KB with Brotli |
| The same, offering only AES-128-GCM, ChaCha20-Poly1305, X25519, P-256 and P-256 signatures, which plxd also accepts | 447 KB, 180 KB gzipped, 147 KB with Brotli. Not worth a second provider |
| A full TLS 1.3 handshake, both ends in WASM, Node 22.23 | 0.57 ms (median of 5 runs of 100, range 0.55 to 0.59) |
| Bulk data with `TLS13_AES_256_GCM_SHA384`, encrypted by one end and decrypted by the other, both in WASM | 44.5 MiB/s (median of 5 runs of 64 MiB), so the client's decrypt alone is about twice that |

Uncompressed, the module is 14% of the renderer build's 3.3 MB (0065), loaded once and cached. A connect's cost is its round trips through the relay (tens of milliseconds each), not the handshake's half a millisecond, and the relay's 2 GiB a day caps traffic far below what the module can decrypt. Not measured: Chrome, Firefox, and Safari themselves (V8 in Node should match Chrome, Safari's JavaScriptCore wasn't run), the module's compile and instantiate time and its memory on a phone-class browser, and a handshake against plxd through the relay. Building ring's C for WASM needs clang with the wasm32 target and `llvm-ar` (rustup's `llvm-tools`), and rustls needs `rustls-pki-types`' `web` feature for the clock, getrandom's `js` feature, and ring's `wasm32_unknown_unknown_js`.

Why rustls and not the others:

- **subtls**, a TypeScript TLS 1.3 client on WebCrypto, which 0068 named. Its README calls it a proof of concept, "not ready to be used in production", and says it needs auditing. It supports P-256 key exchange and AES-128-GCM only, verifies a chain up to public roots with no pinning hook, and would put a second TLS implementation beside plxd's. Its size wasn't measured, and would be smaller.
- **Other TypeScript clients** (`reclaimprotocol/tls`, node-forge): forge's TLS stops at 1.1, and plxd speaks only 1.3. The rest are unaudited, as subtls is.
- **WebTransport with `serverCertificateHashes`** pins natively, but needs HTTP/3 over UDP straight to plxd, which the relay's Workers don't carry, and the certificate it pins may last at most two weeks, so the pin would change every two weeks instead of being the host id.
- **WebRTC with a DTLS fingerprint** pins natively too, but needs ICE, a TURN server, and a WebRTC stack in plxd beside its TLS. That is new crypto, which 0068 rules out.
- **A protocol of our own** (Noise, libsodium) would mean a second handshake in plxd. Also new crypto.

### Streams the hosted client opens are marked, and see less of plxd

- **The relay marks them.** A ticket minted for the hosted client's OAuth application, and every guest ticket, opens a stream whose `open` frame to plxd says so: `client: "hosted"`, or `guest: <linkId>`. Such a stream never takes a spare, since plxd joins a spare before any client exists (`relay/src/host.ts`) and couldn't know who took it. It always gets a new stream with its mark.
- **plxd serves them less.** On a hosted stream, plxd serves only account sign-in and its approval (`/api/auth/account`, `/api/auth/approval`) and `/ws`. On a guest stream, only `/api/auth/guest` and the guest's `/ws`. Everything else, including the descriptor, LAN pairing (`/api/pair/*`), peer sign-in, and webhooks, gets 404 and the stream closes. While the computer's `hostedClient` setting is off, plxd refuses both kinds of stream outright.
- **What a lying relay can do with the mark** is drop it, which makes the stream an ordinary one the relay could already open for the host's own user. It gains nothing it lacks today. Under the hosting choice below, the relay's operator isn't the client's publisher, so a bad publisher can't drop it. Under the alternative, where one Cloudflare account holds both, it can.

### Where the pin comes from

- **A browser device takes its first host id from a link** that Settings > Connections > Open in a browser shows, on the desktop or the phone, as a link and a QR code with the computer's host id in the URL fragment (`#connect=<hostId>`). The fragment isn't sent in any HTTP request (RFC 3986 §3.5). The relay's host list never supplies a pin.
- **The browser can't tell that link from a crafted one.** A phishing link with an attacker's host id fails against an honest relay, which refuses a ticket for another user's host. With a compromised relay that registers the attacker's host under the victim's account, the browser would pin a fake computer, and then take that computer's word for the others. The user's real computers stay pinned and unreadable, but the user might send work and secrets to the fake one, which is the PLX-1316 exposure 0091 accepts for phones.
- **So the first host counts only after the user confirms its code.** On the first connection, the browser shows the computer's name and 0091's commit-reveal code, which binds the host id and the browser's key. The user's devices that already use that computer show the same code with Allow. The browser then asks the user to confirm that the same code appeared on a device they already use, and sends nothing but its sign-in until they do. This doesn't rest on the user's devices staying quiet: a compromised relay can list the fake computer to them too, and under 0091 a computer nothing vouches for gets a "new computer" comparison prompt on the desktop. What protects the browser is that every code is computed per request, from random values both ends commit to before either reveals, plus the host id and the requesting key. The browser's request to the fake computer and any request the fake computer stages on a real device are different requests, so their codes match only by chance, about one in a million. This uses a comparison the flow already has, rather than a second fingerprint screen, and it binds the browser's own key, where a fingerprint shown beside a link would bind only the host. Requiring a QR code instead wouldn't help, since a QR code is a URL too and can be crafted. What's left: a user who sees a prompt on a real device with the expected computer's name and confirms in the browser without comparing the digits. A compromised relay can stage exactly that prompt, timed to the browser's request, so the browser and the dialog both say to compare all six digits.
- **Further hosts come from that host's lists**, by pinned id, as on the desktop: a host in its `approvedHosts`, never `allowedHosts`, and never one the relay lists alone. The relay's list says only which of them are online.
- **A guest takes its pin from the link** (below). A guest gets one read-only thread, and the link comes from the person sharing it, so there is no second device to confirm against.
- **What stops the relay's operator substituting a key:** the pin is the thumbprint of the key, and the TLS handshake proves possession of it, so a relay that presents another key fails the handshake before a byte of HTTP.

### A browser becomes a device

- **Off by default, per computer.** A host setting, `hostedClient` (Settings > Connections), is off until the user turns it on. While it's off, plxd refuses every hosted or guest stream and every hosted-client key, and closes their sockets. Turning it on lets them back in, as 0065's `remoteWeb` does.
- **Each computer decides for itself, at every sign-in.** Approved keys sync between the user's computers (0091), so a browser approved on one computer reaches the others by merge. Each plxd therefore judges the key's kind at every sign-in from the token's `client_id` and from the stream's mark, never from a kind another computer recorded, and refuses it while its own `hostedClient` is off.
- **Sign-in, with no script from Clerk.** The hosted client loads no script from any `parallax.codes` host. Clerk's Frontend API (`clerk.parallax.codes`) and Account Portal sit in the zone on the relay's Cloudflare account (0067), and Clerk's JavaScript SDK loads its code from there, which would give that account script in the client's origin. So there is no Clerk SDK, and the CSP's `script-src 'self'` enforces it. Sign-in is a hand-written OAuth authorization code flow with PKCE (S256) over `fetch`, as the desktop's `account.ts` does (0067): the page makes the verifier and `state`, navigates to Clerk's `/oauth/authorize` in a new OAuth application whose redirect is the client's own origin, checks `state` on return, and trades the code at `/oauth/token`. PLX-1619 must confirm that Clerk's token endpoint answers CORS for the client's origin. If it doesn't, that comes back to Ryan. Clerk's pages are a navigation, not script in the client's origin, but whoever holds the relay's account can still phish that page and collect tokens. A token alone still gets no session without Allow.
- **The token is narrow.** The application asks for `profile email`, not `offline_access`, so the page holds no refresh token, only an access token that lasts a day. The browser signs in again after that, through Clerk's consent screen (0067). It also costs a sign-in per computer: plxd takes an account sign-in only with a token issued within 60 seconds, with 5 minutes of clock skew (`FRESH_SECONDS` and `CLOCK_SKEW` in `daemon/src/clerk.rs`), and a page without a refresh token can't get a fresh one. So each computer the browser signs in to beyond the first that minute, such as one added later from its first host's lists, takes a full trip through Clerk's sign-in and consent. Neither loosening plxd's freshness check nor bringing back `offline_access` is an acceptable fix: the first lengthens how long a caught token works at every host, and the second puts a token that never expires in page script. The relay accepts this application's tokens on `GET /v1/hosts` and `POST /v1/hosts/<id>/tickets` only, and refuses them on every other route, such as `DELETE /v1/hosts/<id>` and `POST /v1/devices`. That includes `/v1/hosts/<id>/connect` with the token in its `Authorization` header (`relayed()` in `relay/src/index.ts`), which sits outside the route list, may take a spare, and opens an unmarked stream. A bad build could otherwise send its token to a server, open an ordinary stream from there, and reach LAN pairing with `hostedClient` off. A hosted-client token opens a stream only through a ticket, which marks it. CORS doesn't protect these routes, since a bad version or an XSS can send the token to a server and call the relay from there. What a stolen token can still do for its day is list the user's hosts and spend their opens.
- **plxd knows the hosted client from the token.** The access token carries the application's `client_id`, signed by Clerk, so plxd knows a sign-in came through the hosted client from the token, not from anything the client says. The hosted client can't get the desktop's token, whose redirect is loopback only.
- **Reaching a host.** A browser's WebSocket can't carry an `Authorization` header, so the client gets a one-time ticket with `fetch` (`POST /v1/hosts/<id>/tickets`, which the relay answers with CORS for the client's origin only) and opens `/connect?ticket=`. That is 0068's ticket path: the anonymous limit at the open, the host's owner, its 30 opens a minute, 16 streams, and 2 GiB a day, plus the mark above. It costs one round trip more than `plxd dial`'s token-in-header open.
- **Approval.** Inside the pinned TLS, the client posts its token and a DPoP proof to `/api/auth/account`, as any new device does, and gets a pending answer. Its screen and the user's approved devices show 0091's commit-reveal code, and the user clicks Allow on one of them if the codes match. A token alone gets nothing.
- **Read-only by default.** The Allow dialog names the request as a web browser and has Read only ticked. Approved that way, the key gets 0091's one-way read-only mark. Unticking it gives full access. Since the mark can't be lifted later, a browser approved read-only reaches full access only by starting over with a new key and a new Allow, as 0091 has it.
- **No pairing code on the hosted client.** A bad version of the client could ask the user to "pair this browser" with the code from Settings, which would give a full-access SPAKE2 session that no switch refuses. plxd refuses `/api/pair/*` on hosted streams, so that form gets nothing.
- **The key** is a WebCrypto ECDSA P-256 key generated with `extractable: false` and kept in IndexedDB, and the client asks for persistent storage. Script on the page can't read its private part, but can use it while the page is open, so "non-extractable" stops the key being copied out, not being used by the code that runs there. Safari deletes a site's script-writable storage after 7 days without a visit, unless the client is installed to the home screen, and then the browser asks again as a new device.
- **Revocation.** A browser is listed in Settings > Connections with its kind and removed as any device is: it joins the removed lists, plxd signs a removal for the user's other computers (0091, PLX-1367), and its sessions end. Signing out in the browser deletes its key. Turning `hostedClient` off cuts every browser on that computer at once.

### What the hosted code can do, and what limits it

The browser runs whatever the client's origin serves on each load. Whoever can publish to that origin can ship code that reads every thread the browser opens, sends it anywhere, uses the device's key and Clerk token while the page is open, and with full access runs agents and terminals on the user's computers. Pinning and end-to-end TLS don't help, because that code is one end of the TLS. Nothing on the page can prevent it: Subresource Integrity and a Content Security Policy are declared by the same HTML the publisher serves, and a published hash protects only someone who checks it at the moment of the load. A bad version can also be served to one visitor once and leave no trace.

That publisher is the honest boundary. The desktop app, the phone app, and plxd also run code published from this repository, so a hosted client published the same way adds no new party. The publishers include anyone holding Ryan's GitHub session, which every agent on his machines uses, as they already do for the desktop app's releases. Two things still make the hosted client weaker than an installed app: a page is fetched on every load, so a bad version reaches users at once, and it can be served to one person, where an app update is one signed file that everyone gets.

What limits it, and is real:

- **Not the relay's operator.** The client, and every script it runs, is served from outside the Cloudflare account that runs the relay (below), so a compromised relay, Worker deploy, or Cloudflare account still can't read a thread, which is 0068's promise. This is the narrowest form that keeps it.
- **One pipeline, in public.** The client is built by `release.yml` from a tagged commit of the public repository, the same run that builds the desktop app, and deployed as exactly those files. Changing it means a public commit and a release, as changing the desktop app does.
- **Published hashes.** Each release lists every file's SHA-256 in its `SHA256SUMS`, and the site serves the same list. `plx web verify` fetches the live site and compares. This detects a swap after the fact. It doesn't stop one.
- **A separate origin** that serves nothing else, so its keys and token are reachable only by its own code. A CSP meta tag allows only its own scripts, `wasm-unsafe-eval`, and connections to the relay and Clerk, and the page refuses to run in a frame. Subresource Integrity covers the built tags. These keep out injected and third-party code. They don't stop the publisher.
- **Off by default, read-only by default, less of plxd.** A computer is exposed only after its user turns `hostedClient` on. A read-only browser can't write, start agents, or open terminals, so code gone bad can read what that browser could, not act on the computer. A hosted stream can't pair, and the token can't remove hosts.

The desktop app and the phone stay the clients that need no trust in a served page.

### Where the client is hosted

- **Recommended, and what this record assumes: GitHub Pages**, on a `github.io` origin that serves only this client, with no custom domain. GitHub already holds the code and the releases the desktop updater installs, so it adds no party, and its DNS isn't on the relay's Cloudflare account, as `parallax.codes`' is. A user's project sites all share one origin (`<user>.github.io`), so the client needs a GitHub organization of its own, whose site is the client.
- **The alternative: `app.parallax.codes`**, a Cloudflare Worker with static assets, apart from the relay's Worker. It has a better address and can send headers (a real `frame-ancestors`), but it is on the same Cloudflare account and zone as the relay, so whoever controls that account controls the code and the relay together, and can drop the stream marks above. A compromised relay account could then read what browsers open, which is the weakening Ryan's rule forbids. It's Ryan's call (below).
- **Build and publish.** `release.yml` builds the client once per release and attaches it with its manifest. A deploy workflow, run only by hand (`workflow_dispatch`), publishes exactly that release's files. The credential that writes to the organization's site lives in a GitHub environment, `hosted-client`, whose deployment rule admits only stable release tags. The rule is the exact stable format, `v[0-9][0-9][0-9][0-9].1[0-9][0-9][0-9][0-9].1[0-9][0-9][0-9][0-9]` (`v<YYMM.1DDHH.1MMSS>`, [0030](0030-release-versions.md)), never `v*`, which would also admit `-nightly` and `-dev` tags. The workflow checks the same pattern, anchored at both ends, and refuses any other ref. A pull request branch, a nightly, or an edited workflow on another branch can't reach the credential. Production deploys are Ryan's. That is a rule, not a gate, since anyone with Ryan's GitHub session can make a stable release, so agents never run the workflow, as they never deploy the relay's production Worker. Under the alternative, the deploy is `wrangler deploy` by Ryan from the client's own directory.

### Guest links: one thread, one browser

- **Who.** The owner of a thread, from a full-access session on the desktop or the phone: the thread's menu has Share with guest. A read-only device can't make one, as it makes no pairing codes. It needs `hostedClient` on for that computer, since guests use the hosted client.
- **The link** is `https://<client>/g#<hostId>.<linkId>.<secret>`: the host id (the pin), a 16-byte link id, and a 32-byte random secret, base64url. All of it is in the fragment, so no server gets it in a request, though the client's own code reads it, and the browser's history and sync keep it. plxd and the guest's browser each derive two keys from the secret with HKDF-SHA256: a relay pass and a host key, under different labels, so one tells nothing about the other.
- **Opening it takes a click.** The guest page does nothing on load beyond showing an Open button. Only a click in the page makes the guest's key, asks for a ticket, and binds the link. Mail and chat scanners (Safe Links, Proofpoint) load links in headless browsers that run script, and binding on load would let one take the link from the real guest.
- **Passing the relay without an account.** plxd sends the relay, over its authenticated control socket, the link id, the SHA-256 of the relay pass, and the expiry, and withdraws them on revoke. The guest's client asks `POST /v1/hosts/<id>/guest-tickets` with `Authorization: Guest <linkId>.<pass>`. That request goes through the anonymous limit (120 a minute per address and host) before any object runs, then the pass and its expiry, then the host's online check and the guests' budgets below. The ticket opens `/connect?ticket=` once, on a new, marked stream. At most 20 links are live per host at the relay. Nothing in the connect limiter is skipped.
- **Guests have their own budgets, below the owner's.** All of a host's guests together get at most 10 opens a minute, 4 open streams, and 256 MiB a day, and each link at most 6 tickets a minute, 2 open streams, and 128 MiB a day, which the relay counts on the guest's marked stream. Guest traffic still counts in the host's totals, so 0068's cost ceilings don't move, but guests stop at their share, so the owner always keeps at least 20 opens a minute and 12 streams. Bytes are counted from the streams' reports, which come every 8 MiB or within 5 minutes of a frame (`REPORT_BYTES`, `REPORT_AFTER` in `relay/src/stream.ts`), so the guests' 4 streams can pass their 256 MiB by under 32 MiB before the relay closes them. The owner's floor, net of that, is 1,760 MiB a day. A guest past its share has its streams closed until the next UTC day, and the owner's aren't touched. plxd also limits a guest session's reads (`thread/read` and the like) to 10 a minute, so one guest can't spend the share in a loop. What's left: one link's holder can use up the guests' share and lock out the other guests, but not the owner.
- **Passing plxd.** Inside the TLS pinned to the link's host id, the guest posts the host key and a DPoP proof from a non-extractable WebCrypto key to `/api/auth/guest`, the only sign-in a guest stream serves. The first browser's key binds the link, opening it again in that browser works, and any other key is refused, as T3's link works in one browser. The relay saw only the pass's hash, and the pass doesn't derive the host key, so the relay can count a guest but can't be one.
- **Expiry and revocation.** A link lasts 24 hours, as T3's does. Expiry, Stop sharing, a new link for the same thread (one live link per thread), archiving or deleting the thread, and turning `hostedClient` off each end it, and each closes a live guest session at once. plxd decides, and the relay's copy only limits traffic, so a relay that ignored a revoke still gets a refusal from plxd.
- **What a guest sees: read-only by default.** The thread's transcript and its live events, as T3's guest sees: messages, replies, tool calls and their output. Anything the agent read or printed can show, and the share dialog says so. With "can suggest messages" ticked (off by default), the guest's message waits at the end of the thread until the owner sends or dismisses it, as T3 has it, and a sent message runs as the owner's turn with the thread's permissions.
- **What a guest never reaches, both ways.** Coming in, a `guest` level in plxd's exhaustive method match, beside full and read-only, allows a short list of reads, each checking the thread id. It refuses any other thread or project, files, diffs, terminals, settings, secrets, approvals, starting or stopping a run, device and host lists, other computers, the push key (0100), and the account. Going out, the read-only level gates only what comes in (`methods/read_only.rs`), and `events/event` reaches every subscribed connection, so a guest connection gets its own outgoing filter that denies by default: it passes an allow-listed event kind only when its thread id is the link's thread, and drops everything else, including host-wide notifications and any new kind added later. A guest isn't a device: it never joins the approved lists and never syncs.
- **What the owner sees.** Whether the link has been opened, and when it was bound. plxd sees a relay stream with no address, so it doesn't claim more. An owner who didn't expect the time shown can Stop sharing and send a new link.
- **Limits.** A link leaked before its guest opens it gives the thread to whoever clicks Open first. A link leaked after that can still spend that link's share of the guest budget until it's revoked. The hosted client's publisher can read what a guest sees, as above.

#### How plxd does it (PLX-1618)

- **Keys.** HKDF-SHA256 over the 32-byte secret with no salt, 32 bytes each, `info` `parallax guest relay pass v1` for the relay pass and `parallax guest host key v1` for the host key. plxd keeps only the SHA-256 of each and the bound key's thumbprint. `guest/create` answers with the fragment `<hostId>.<linkId>.<secret>` once, and nothing reads the secret back.
- **Links live in plxd's memory.** A restart ends every link, which fails closed. At most 20 are live, one per thread.
- **The relay's copy (PLX-1616).** plxd sends `{"t":"guests","links":[{"link","pass","expires"}]}` on its control socket whenever a link starts or ends, and on connecting when it has any: `pass` is the hex SHA-256 of the 32 pass bytes, `expires` is seconds since the epoch, and a link missing from the list is withdrawn. The relay forgets them when that socket closes. plxd also refuses unjoined a stream marked with a link that isn't live.
- **Sign-in and socket.** `POST /api/auth/guest` takes `{"hostKey": <base64url>}` and a `DPoP` proof with no access token, for the link the stream's mark names, and answers `{threadId, expiresAt, canSuggest}`. A wrong host key and an ended link get the same 401. The guest's `/ws` takes no ticket and no session, only a proof from the key that bound the link. Only that request binds, so opening a stream or a socket first binds nothing.
- **The guest level.** A guest calls `orchestration/subscribeThread`, `orchestration/threadHistory`, and `events/unsubscribe`, and `guest/suggest` when its link allows it, each naming the link's thread. Its snapshot leaves out the thread's permission requests, background tasks, and watched pull requests, and its snapshot, pages, and live events hold only `agent.started`, `agent.updated`, `agent.output`, `agent.finished`, and `thread.reverted` of that thread. It gets no other notification, `host/updating` among them. `agent/image` isn't on the list, so a guest sees no image a message carries.
- **Reads.** Every request on the list counts against the link's 10 a minute, across its connections. A request off the list is refused before it counts.
- **Suggestions.** At most 5 wait on a link, in `guest/list`. `guest/send` sends one as the owner's `agent/send`, and `guest/dismiss` drops it. Nothing tells the owner's apps when one arrives yet, so they read `guest/list`.
- **Ending.** Expiry, `guest/revoke`, a new link for the thread, a `thread.updated` that archives it or a `thread.deleted` for it in the event log, whichever path wrote it, and `hostedClient` off each end the link, close its connections, cut its relay streams, and resend the relay's list.

## Rejected

- **Serving the client from `parallax.codes` without saying so.** It weakens 0068's promise for every browser user, and the rule says never.
- **Clerk's JavaScript SDK.** It loads its code from the Frontend API in the relay's zone, which would undo the hosting choice.
- **Taking a browser's first host from the relay's list**, as a new phone does (0091, PLX-1316). The browser is the client whose code is least fixed, so its first pin comes from a link the user was given, and counts only after a code they confirm.
- **Guests sharing the owner's relay budget.** One guest could then spend the day's 2 GiB and close the owner's streams until 00:00 UTC.
- **Guest links as devices with a read-only mark.** A device spans every computer and syncs. A guest gets one thread on one computer, which the read-only level doesn't express.
- **A guest message that runs without the owner.** It would let anyone with the link direct an agent with the thread's permissions.
- **A service worker that pins the bundle after the first visit.** The server can replace the service worker, so it adds no protection a published hash doesn't.

## Consequences

- A browser reaches the user's computers from anywhere, through the relay only, so every byte counts against the host's 2 GiB a day.
- Before this record, only the host's own user could open a stream to plxd's listener through the relay. Now a guest link's holder can too, onto a marked stream that serves guest sign-in and one thread only.
- The relay learns which guest links exist, when they're used, and from which address. Not their content, and not the host key.
- Thread content stays unreadable to the relay and Cloudflare. It isn't private from whoever publishes the hosted client, the same party that publishes the apps, and a browser user trusts each page load where an app user trusts each update.
- A browser signs in again each day and once more for each further computer, and Safari users without the home-screen install re-approve after a week away.
