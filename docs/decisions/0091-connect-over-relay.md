## Context

Parallax Connect (0056) works only when every computer is on one Tailscale tailnet. plxd listens on its Tailscale IPv4, port 7340, and admits a connection after `tailscale whois` names its own untagged user. The app finds computers with `connect/devices` (`tailscale status`), reaches them with `plxd dial <tailnet ip>`, and runs installs and CLI sign-ins on them over ssh to the Tailscale IP (`apps/desktop/src/main/hosts.ts`, `sshOf`). The phone reaches them the same way (PLX-983). plx-connect's `add` needs ssh and Tailscale on both ends. Tailscale is in about 50 files across plxd, the protocol, the store, the desktop app, the phone, and plx-connect. Ryan wants Connect to be Parallax's own tunnel, so Parallax controls every part of it, and as close to T3 Connect as possible.

T3 Connect, read at T3 Code `a773dc38` (`docs/internals/t3-connect.md`, `remote.md`, `environment-auth.md`, `docs/user/remote-access.md`):

- **Setup.** `npx t3 connect` on the host signs in with Clerk, offers the background service, and links the environment. A CLI with a browser uses loopback PKCE, started on the hosted `/connect` page so sign-in survives the redirect. Over SSH or headless it uses Clerk's OAuth device authorization grant: the CLI prints a link and a short code, the user approves on any device, and the CLI polls Clerk's token endpoint. `t3 connect unlink` stops exposure and keeps the sign-in. `t3 connect logout` clears it.
- **Discovery.** Any device signed in to the same account lists the account's environments and picks one. No pairing. The list has no timer: it refreshes when a screen that shows it opens, when the network comes back, and when the sign-in changes (`packages/client-runtime/src/relay/discovery.ts`).
- **Transport.** The relay provisions a managed Cloudflare Tunnel per environment and the host runs a pinned `cloudflared`. After setup the relay is out of the data path, except webhooks. Cloudflare ends TLS at its edge, so it can read the traffic.
- **Trust.** The relay is "a trusted broker": for a signed-in user with a linked environment, it asks the environment to mint a one-time bootstrap credential bound to the client's DPoP key, and the client trades it with the environment for a session. A compromised relay signing key is outside what DPoP protects.
- **Routes.** A saved environment keeps an ordered route list. The server reports its LAN and tailnet addresses, the client saves them as learned routes, connects over the first route that answers, and while on a later route re-checks earlier ones every minute and on network changes, moving back when one works. Pairing once through T3 Connect is enough to use the LAN at home.
- **Limits.** 3 machines per account, raised by a paid T3 Chat plan. Phones and browsers don't count. Idle tunnels are removed after minutes offline and recreated on wake at the same address.

Parallax already runs most of this. Parallax Relay (0068) is live at `relay.parallax.codes`: plxd keeps one authenticated WebSocket to it, a client signed in as the host's user gets a one-time ticket for a stream, and plxd joins the stream to its own TLS listener, so the relay carries only ciphertext. plxd's listener (0065) has TLS with its own P-256 key, DPoP-bound scoped sessions, 30-second WebSocket tickets, and a public descriptor that reports its LAN addresses as routes. A host's relay id is the JWK thumbprint of that key. Since PLX-1146, signing in to the desktop app registers its own computer and every Connect computer with the relay, and the token stays on the computer where the user signed in. plxd owns terminals (0064), so a remote shell no longer needs ssh.

What's missing: reaching a computer through the relay needs a SPAKE2 pairing code first, computers are found through Tailscale, nothing sets a computer up the way `t3 connect` does, and some installs and sign-ins still use ssh to a Tailscale IP.

## Decision

### Ryan's calls

Ryan answered these on 2026-10-30.

1. **Trust.** Account sign-in plus a one-time approval of each new device and each new computer with a 6-digit code (below, "Access"). A token a compromised relay catches then gets no session. The choices not taken were sign-in alone, as in T3, which lets a compromised relay that catches a token get a session on the user's hosts, and a pairing code per client and host (0065).
2. **Tailscale.** Tailscale stays as an optional direct route (below, "Tailscale becomes an optional route"). The account and the relay replace it for finding and admitting computers. The choice not taken removed it entirely.
3. **Delivery.** One Linear issue per part, and one pull request for all of them (below, "Work").
4. **The npm name.** The CLI is `plx`, so setup is `npx plx connect` (below, "Setup"). `plx` on npm is held by another user's placeholder (0.0.1, "Coming soon", last changed 2022-06-24), so Ryan asks its owner for it, then npm support under its package name dispute policy. Until it transfers, the CLI publishes as `plx-cli` with a `plx` command (`npx plx-cli connect`).

### Access: a signed-in client gets a session without a code

- **The host is pinned by its id.** A client reaching an `account:` host over any route accepts plxd's certificate only when the JWK thumbprint of its key equals the host id. The relay can't present another key for that id, so it can't stand in for the host or read the stream. SPAKE2 is no longer needed to vouch for the key.
- **plxd records its account.** When the host registers, plxd stores the Clerk user id of the token it was registered with. For PLX-1146's signed registration, where plxd never sees the token, the signing computer's app passes the user id with `relay/sign`. That app reaches plxd over a connection plxd already trusts. The relay never sets it, so a compromised relay can't swap in its own account. Amended 2026-11-06 (PLX-1049): plxd stores the issuer it checks tokens against beside the user id, and one recorded before plxd kept it is the development instance's. An account recorded under another issuer counts as none ([0067](0067-clerk-accounts.md)).
- **plxd checks the token itself.** Inside the pinned TLS, the client posts a Clerk token and a DPoP proof to `/api/auth/account`. plxd makes every check `packages/clerk-verify` makes, against the Clerk instance the apps sign in to, which the relay also trusts: the development instance until the account move ships (PLX-1465), then production (PLX-1049): RS256 against its JWKS (cached, refreshed on an unknown `kid`), issuer, `exp` and `nbf` with its skew, no `aud`, an OAuth token's `client_id` in the app's allowlist, a session token's `sid`, and `azp` in the allowed origins where present. It also requires `sub` equal to its account, and `iat` within the last 60 seconds by plxd's own clock, with 5 minutes of skew either way. Never by the relay's clock: plxd corrects its relay proofs by the relay's time (0068), and a compromised relay could use that to make an old token look fresh. The skew keeps a computer whose clock is a few minutes off from refusing every sign-in, and stretches how long a captured token works to about 6 minutes. A computer more than 5 minutes off refuses account sign-ins, and logs the offset it measured from the relay so the user can fix its clock. If the client's key is approved (below), it then issues its ordinary DPoP-bound `admin` session (0065), listed in Settings by device and revocable like a paired one.
- **A token goes to a host once.** The client sends a token only to a host it has no session with, and gets a fresh one from Clerk for it (an OAuth refresh, on the desktop and the phone alike), separate from the one it sends the relay to open the stream. After that it uses its session.
- **A new device or computer is approved once.** Sign-in proves the account. Approval proves the request came from one of the user's own devices, so a token alone gets nothing.
  - A host keeps the DPoP key thumbprints of its approved clients and the account's approved host ids. A signed-in client whose key isn't approved gets a pending answer, not a session.
  - For a new device, both ends of a pending request show the same 6-digit code, made from random values both sides commit to, as Bluetooth's numeric comparison does. The host sends a hash of its random value, the client sends its own, then the host reveals its value. The code is a hash of both values, the host id, and the client's key thumbprint. Neither side can pick its value after seeing the other's, so a relay in the middle of a request gets one chance in a million to make two screens match, however many keys it tries.
  - A host holds one pending request at a time, at most 5 an hour, and drops one after 10 minutes. No new request replaces a pending one before then unless the user denies it, so a relay can't wear the user down with prompts. The client enforces the same on its side, since a fake host sets none: it keeps a request's random value and the host's commitment for its 10 minutes and reuses them when it reconnects, treats a different commitment from that host id as a failed request, and starts a new request only when the user asks, at most 5 an hour. A relay that drops the connection therefore gets no new code to try.
  - A new computer: `plx connect` ends by showing a random 6-digit code and waiting. A signed-in client that reaches the host shows a dialog asking for that code, and the user types it there. The two run 0065's SPAKE2 pairing with it, so the host approves the client and the client approves the host, and nothing is typed in the terminal. Typing proves the user saw the terminal, which a click on the client alone can't. Someone who didn't see it gets one guess per attempt, within the host's 5 an hour, and the code changes after 10 minutes. A typed code is good for one pairing run: a failure, or a connection that drops after the app sent its pairing message, throws it away and the user types it again, and the app allows at most 5 runs an hour per host. So a fake host the relay lists, where the host's own limit doesn't apply, also gets one guess per run the user starts. A typed-code attempt is never held pending: each run succeeds or fails at once and counts toward the 5 an hour. The terminal then prints the approved device's name. That client then copies approved client keys and host ids between the new host and the hosts it already has sessions with, so the user's other devices need no step for it.

### Routes: the LAN first, the relay always

- An `account:` host's routes are its learned LAN addresses first, then its Tailscale address when plxd reports one, then `relay:<hostId>`. ### Speed: connecting as fast as T3

Once connected, a message makes one trip either way, so the relay matches T3's tunnel. Opening a connection is where the relay costs extra round trips, so:

- **Direct and relay routes at once.** The app starts the LAN and Tailscale routes together, starts the relay route 200 ms later if neither has answered, and keeps whichever connects first. Away from home a LAN address can take seconds to time out, and this stops the app waiting for it. A connection that lands on the relay moves to a direct route at the next re-check that answers.
- **No separate ticket request.** The client opens `/v1/hosts/<hostId>/connect` with its Clerk token in the `Authorization` header, never the URL, as 0065 and 0068 keep tokens, and the relay checks it there instead of issuing a ticket first. 0068's 30 tickets a host a minute become 30 stream opens a host a minute.
- **A spare stream.** plxd keeps one idle stream open to the relay, so the relay joins a new client to it without first asking plxd to open one. It counts against the 16-stream limit. The host object commits the exclusive claim before returning its id, then owns the stream object’s cleanup notification through `ctx.waitUntil`, independently of the client Worker’s lifetime. That notification no longer delays the client upgrade (PLX-1468). It carries the claim-time 30-second deadline and only arms an existing stream with no client socket, so arrival, close, or hibernation before its delivery cannot re-arm a joined or ended stream. Storage input gates order its alarm write with join’s alarm deletion. Pending RPC work prevents ordinary eviction, per [Cloudflare’s lifecycle contract](https://developers.cloudflare.com/durable-objects/concepts/durable-object-lifecycle/), but is not a durable queue across forced shutdown, which terminates sockets. Control reconnect still reconciles held streams.
- **The proof opens the channel.** A client with a session sends its DPoP proof with the WebSocket upgrade to `/ws`, instead of first trading it for a 30-second ticket. The ticket stays for clients that can't set upgrade headers, such as a browser. This saves a round trip on the LAN too.
- **A Durable Object per stream.** Each stream's bytes cross their own Durable Object, not the host's, so a large transfer on one stream doesn't queue another. The host's object still counts: it admits each stream against the 16 open, and a stream's object reports its frames to it every 8 MiB and when it closes, which is how often 0068 already saves the count. When the host's 2 GiB a day is spent, the host's object closes its streams' objects and refuses new opens. This holds when plxd's listener fails after answering too. A stream the relay closed, or whose close it answered, gets no `gone`. Any other end, such as a failed send, an unanswered ping, or no answer to the close, still sends it. Under `wrangler dev` the answer comes back within about 12 ms.
- Amended 2026-11-06 (PLX-1462): **a sign-in takes one stream.** A connect with a session was already one stream, the spare. A new device's sign-in took three, one per request: `/api/auth/account`, the request's value, and the wait for approval, and the last two opened back to back, so they missed the spare.
  - They now go one after another on one pinned TLS connection, with HTTP keep-alive. plxd's listener keeps a connection only after a 202 from `/api/auth/account` or `/api/auth/approval`, the answers a next step follows, and only when the request sent `Connection: keep-alive`. It waits at most 2 s for the next request, since through the relay a waiting connection holds one of the host's 16 streams. That wait takes one of the pending slots a new connection's request takes (16, and 6 per address), so kept connections can't outnumber them, and with none free the connection closes. Every other answer closes the connection, as before, a refusal included. Each request still carries its own DPoP proof, so a kept connection grants nothing.
  - The client reuses a kept connection only for the same route and pin within 1 s. After a pause for the user, such as comparing codes before Allow, it opens a new one, and the host has closed the old one by then. A kept connection the host closed sooner, such as on a slow link, gets no answer, and the step then goes once more on a new connection with a new proof. Sending the same step twice is safe. A plxd from before this answers `Connection: close`, and the client then opens a connection per request, as before.

What a round trip pays over T3's tunnel (94 vs 56 ms on 2026-11-06) is each frame's two extra legs through the object, which a hint can't remove.
- Amended 2026-11-09 (PLX-1483): **the first frames go behind the upgrade.** With the proof on the upgrade, a client still waited one round trip to the computer for the 101 before `initialize` could go. `plxd dial` now sends the lines already waiting on its input, which are the app's `initialize` and first subscriptions (PLX-1480), as frames in the same TLS record as the `/ws` request. The 101, `initialize`'s answer, and the first event come back together.
  - **The TLS handshake says whether a host keeps them.** plxd's listener lists the ALPN protocol `plxd-early-ws` ahead of `http/1.1`, and `plxd dial` offers both. Only when the handshake picks `plxd-early-ws` does the client send anything before the 101. The answer comes from the plxd answering that connection, in the handshake the client already makes, under the pinned certificate. So it costs no round trip, the relay can't change it, and nothing is saved that a rollback could make wrong. A capability saved from an earlier `initialize` was the choice not taken: after a rollback the old host drops whatever part of the frames it read with the request, which breaks the WebSocket's framing and leaves the connection to time out. The handshake's round trips, certificate, and pin don't change. It is TLS 1.3 with no 0-RTT, and nothing is resumed, since each dial builds a new client configuration that holds no earlier session.
  - **The host checks first.** plxd keeps what it read behind the request, under 1 KiB since it reads 1 KiB at a time, as bytes it doesn't parse, and reads nothing more until the upgrade is decided. It then checks what it checked before, in the same order: the session's token, the proof and its key, replay, the browser switch, revocation, and the read-only level. Only after the 101 goes out do the kept bytes reach the WebSocket, so those frames are handled as later ones are, and a read-only device's write gets the same refusal. A refused upgrade is answered as before, and the bytes are dropped unread.
  - **Old and new.** A plxd from before this lists no protocol, so nothing is picked and the client waits for the 101 as before. That covers a host rolled back to an older version, from its next connection. A client from before this offers no protocol and sends nothing early. A browser, URLSession, and OkHttp offer `h2` and `http/1.1` and get `http/1.1`, which they already speak to plxd. A client whose ALPN list has neither `plxd-early-ws` nor `http/1.1`, such as one offering only `h2` or `http/1.0`, now fails the handshake, where the listener used to ignore any list. The gain needs this version on both ends: the plxd that dials, which ships with the app, and the plxd that answers.
  - **Limits.** At most 8 KiB of frames go early, so the request and the frames fit one TLS record. A host that refuses has then read everything the client sent, so its close is clean and the client reads the 401. A client that sent more could lose the refusal to a connection reset, which costs only that client. Lines past 8 KiB go after the 101, and `plxd dial` never waits for input before it sends the upgrade. When an upgrade is refused and the ticket path then opens a socket, the same lines go there, since the host dropped them. When the connection fails after the upgrade went out and before the client read the 101, the client can't tell whether the host ran the early lines, so a caller that pipes a write into `plxd dial` as it starts must not send it again blindly. The app puts only `initialize` and subscriptions there, which belong to the connection.
  - **The 101 still takes one round trip after TLS, and nothing waits for it now.** The host learns who the client is from the client's first flight after the handshake, so it can't admit the session sooner. Admitting it inside the handshake would put the credential in the ClientHello, which means a pre-shared key or 0-RTT, and neither is used here. A TLS client certificate goes in that same flight, so it saves nothing.
  - The phone's `/ws` goes through `URLSessionWebSocketTask` and OkHttp, which can't write before the 101, so the phone doesn't change until PLX-1502.
  - Measured with `scripts/bench/round-trips.mjs` under `wrangler dev`, medians of 10 dials, with 0, 20, and 50 ms added to each direction of every outer connection. A round trip to the computer crosses two of those connections, so it grows by four times the delay. From `connected` to the first event, with the subscription sent behind `initialize`: 7, 91, and 210 ms before, and 2, 0, and 0 ms after. From starting `plxd dial` to the first event: 46, 414, and 955 ms before, and 38, 323, and 744 ms after. That is one round trip to the computer fewer.

That leaves the trip to the relay and the TLS handshake inside it, about what a T3 client spends reaching Cloudflare and opening its tunnel connection. Measured on 2026-10-29, with the host on an iPhone hotspot and the client at home: Tailscale's direct path took 73–125 ms a round trip, and the two legs through Cloudflare's Los Angeles point of presence took 33–116 ms and about 22 ms, so about 55–138 ms through the relay. ### Limits

- 0068's ceilings hold: 10 hosts per user, 16 open streams and 2 GiB a day per host. Phones and browsers aren't hosts, so they don't count, as in T3. The LAN route keeps most traffic at home off the relay. Amended 2026-11-04 (PLX-1357): `GET /v1/hosts` gives each host `usage`, its bytes today, the limit, and `resetsAt`, the next 00:00 UTC, when the count starts again. plxd passes it on in `relay/hosts`, and the desktop app and the phone read it from the list they already read every 15 seconds. ## Consequences

- Setting up a computer takes one command and a sign-in, with no Tailscale required, and no sshd, keys, or open ports, and every signed-in computer and phone sees it.
- plxd verifies Clerk tokens in Rust: RS256 and a JWKS fetch. `ring` already verifies RSA, so no new crypto crate is needed.
- Connect depends on the relay and Clerk being up. A computer that loses the internet is reachable only on the LAN, and only by a client that already holds a session for it.
- Away from home every byte crosses a Cloudflare Durable Object and counts against the host's daily budget. The measured trip was about level with Tailscale's direct path ("Speed").
- Adding a device or a computer takes one approval that T3 doesn't have.
- Existing Connect computers migrate over one release, with no action from the user beyond being signed in.
- Production Clerk (PLX-1049) has to register `https://relay.parallax.codes/connect/code` as a redirect URI of the desktop app's OAuth application.
- On a network that inspects TLS, a host needs Clerk's host exempted from inspection to accept new account sign-ins (PLX-1363).

Amended 2026-11-06 (PLX-1472): opted-in client upgrades also expose StreamRelay-local
`join_read` (entry through the armed read), `join_ready` (entry through both ready sends,
only when paired), `join_delete_alarm` (elapsed deletion, only when paired), and
`join_total` (entry through lifecycle work, before header/response construction). These
are local monotonic durations in milliseconds, not timestamps. `stream_join` still
measures the Worker's entire object fetch. Its per-request difference from `join_total`
includes RPC transit, pre-entry queue/wake/gates, and response overhead. It cannot
separate those causes or establish that a storage gate caused production delay. Read
and alarm durations include awaited scheduling/storage latency, not just CPU time.
The entry-to-ready and read windows are nested inside total and must not be summed.

For an opted-in spare claim, the existing background taken RPC records volatile
`taken_entry=1`, `taken_read` (entry through armed read), `taken_alarm` (alarm write
elapsed), `taken_total` (entry through completion), and `taken_outcome` (1=set,
2=skipped because joined or ended). Entry/outcome are numeric flags. Join snapshots only
stages already observed in its own uniquely armed stream object. Missing stages mean
unfinished or unavailable, including after eviction, on a non-spare or legacy ticket
claim, or if taken has not entered yet. Absence does not prove taken never ran. These
observations are never persisted, awaited, fetched separately, or reused across armed
streams. No cross-machine clocks are subtracted. The Worker forwards the opt-in only
after admission and emits these headers only on successful client upgrades. New fields
are finite and bounded to 0–60,000; older daemons ignore them and newer daemons accept
headers without them. Diagnostic defaults, all existing storage awaits/gates and stream
lifecycle ordering stay unchanged. This diagnostic establishes no latency saving or
product parity claim and does not authorize production deployment.

Amended 2026-11-09 (PLX-1493): **a stream's alarm writes no longer hold what a client waits for.** Cloudflare holds everything a Durable Object sends, a 101 and a WebSocket message included, until each storage write before it is confirmed by three of five followers in other data centers ([output gates](https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/), [SQLite in Durable Objects](https://blog.cloudflare.com/sqlite-in-durable-objects/)). Setting an alarm also waits for the alarm's scheduler before it commits, behind the scheduler update a deletion left in flight (workerd's `actor-sqlite.c++`). A spare connect made three such writes in the stream's object: the claim set an alarm, the join deleted it, and the first frame set the report's. The 101 and `ready` waited for the first two, and plxd's TLS reply waited for the third. In production that showed as an inner TLS handshake 45 ms longer than the inner WebSocket upgrade on Wi-Fi and 141 ms longer from a GitHub runner, where both are one round trip, and as a `stream_join` with two modes near 35 and 80 ms. Per connect, inner TLS tracked `stream_join` (r = 0.90 and 0.72).

- The stream object's alarm writes on a client's path, which are the claim's, a join's, and a frame's, pass `allowUnconfirmed`. They only bound a wait or time a report, so nothing a client is sent depends on one. A write that then fails still resets the object, which drops both ends. plxd's `gone`, or the alarm that did reach disk, then frees the stream's place, as for any object that reset. The host object's writes, the spare's claim included, stay confirmed before their answer leaves, and so do a stream's `arm` and its end.
- The Worker asks the anonymous limit and checks a client's token at the same time, and waits for both before anything reaches an object. The limit's refusal still comes first. On production the Rate Limiting binding answered at once on some connections and took about 30 ms on others in Los Angeles on 2026-11-09. On staging it answered in 0 ms every time, so this saved nothing there.
- The JWKS is cached per isolate, and most connects reach an isolate without it: `auth` was 0 in 4 of 30 connects from the runner and in none of 90 on Wi-Fi, and on staging a fetch took 32 to 41 ms. A cache isolates share is PLX-1505.
- An opted-in upgrade also returns `limit` (the anonymous limit's answer, from the request's start), `jwks` (the JWKS read, only when this request made one), `host_hop` (a call to the host's object that does nothing, made beside the stream's join once `open` answered), and `worker` (the request's start through the stream's 101). `auth` now starts with the request too and runs beside `limit`, so the two overlap. What `host_open` takes over `host_hop` is the host object's own work, with the claim's confirmation. They come after the older fields, so a plxd from before this prints what it did, and plxd now reads 24 entries, not 16.
- Under `wrangler dev` a write is confirmed at once, so none of this shows there. Measured on staging ([0068](0068-relay.md), PLX-1495) from a GitHub runner, 30 connects before and 30 after, four minutes apart, medians: inner TLS 135 to 27 ms, `stream_join` 56 to 21 ms, connect 381 to 267 ms, first event 467 to 356 ms. A build with no alarm write at all in the stream's object did no better, so the hold those writes caused is gone. What is left in the relay's upgrade there, of about 150 ms: about 40 ms Cloudflare takes to run the Worker at all, which a 404 that does no I/O pays too, the JWKS fetch, 36 ms for `host_open` of which `host_hop` is 5 to 8 and the rest is the spare claim's write being confirmed (PLX-1506), and 16 to 21 ms for `stream_join`. Production's gain needs Ryan's deploy and a Wi-Fi run.
- With the hold gone, a handshake that finishes in under 40 ms meets a 40 ms wait on the inner WebSocket upgrade on a Linux host, which is plxd's listener leaving Nagle on, not the relay (PLX-1512).
