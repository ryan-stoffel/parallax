# Connect timing audit (PLX-1466)

For a future authorized comparison, pin both versions:

```
node scripts/bench/t3-compare.mjs --version 0.1.7 --parallax-tag <exact-tag> --connects 30 --trips 50 --timings --token-file <test-account-file> --out comparison.jsonl
```

This enrolls disposable hosts as before. Do not run it against a personal account. No extra run or enrollment is needed to review this PR. The JSONL now retains both products, the Parallax tag, sample counts, medians and nearest-rank p95. Without `--parallax-tag`, the probe retains its newest-nightly-at-least-one-hour-old selection. Without `--timings`, there are no new diagnostic stderr lines or request headers. Older releases simply provide no stage rows.

Both servers run on the measuring computer, so the access network is traversed twice. T3 terminates TLS at Cloudflare. Parallax has pinned end-to-end TLS and DPoP. Equal sample counts do not make these protocols or security guarantees identical. Keep the process-inclusive measurements, rather than subtracting stages to claim a win.

The comparison forwards the same connect/trip counts and gap to the Parallax probe. Each performs one uncounted connection and RPC warm-up, 2200 ms gaps before counted connects, and 100 ms before counted RPCs. T3 takes an extra uncounted connection for RPCs; Parallax uses its final measured connection. The standalone probe still defaults to 5 connects / 6 trips. Increasing to 30 uses 2200 ms gaps to leave room under the 30 opens/minute limit. Both scripts refuse a gap under 2000 ms, since every dial waits the gap first, so any count stays within the limit. Approval opens and relay-object checks are separate. OS DNS, host/JWKS caches, and the T3 Node process may be warm. Each Parallax dial is a new process with fresh TLS state. A gap gives spare refill time but does not prove that a spare is ready. The relay timing flag records actual spare selection. Earlier results (5/6 vs 30/50, no Parallax warm-up) are not matched before/after evidence, and earlier even-count Parallax medians selected the upper middle sample.

Since PLX-1549 the probe times two dials in turn, 30 of each by default in `t3-compare`, so they share the network. `connect` is the relay alone, `plxd dial --account=<id> -- relay:<id>`, as every earlier run timed it, and it's the number to compare with T3 and with older runs. `appConnect` is the desktop app's dial away from home, `plxd dial --account=<id> -- 10.255.255.1:7341 relay:<id>`. The first route stands in for the computer's home LAN address seen from another network: a private address on none of this computer's networks, whose TCP connect gets no answer. The probe picks it at the start of its stream check from 10.255.255.1, 172.31.255.1, and 192.168.255.1, the first on none of the IPv4 networks Node lists for this computer, and fails that check, saying why, when each is on one (PLX-1571). `appDial.route` records the one it used. Since PLX-1553 plxd gives a head start only to a route that may answer from this computer's networks, so a current plxd starts the relay at once and its `appConnect` sits near `connect`. A plxd from PLX-1549 until PLX-1553 waits 200 ms (`RELAY_HEAD_START`) and opens the relay's outer connection (DNS, TCP, TLS) during it, saying `plxd dial: opened the relay's connection during the head start` on stderr, and `appDial.early` counts those. An older plxd waits the full 200 ms. With `--timings`, `appDial.headStart` counts the app dials whose `relay_route_start` came 100 ms or more after `dial_start`, and the notes say whether the relay waited. Before PLX-1571 the stand-in was a loopback port, which plxd always gives the head start, so earlier `appConnect` numbers include 200 ms that a real away-from-home dial no longer pays. Each stage row names its dial in `dial`. `relay_route_start` marks the relay route's turn, so `outer_tls_ready` minus `relay_route_start` is what the outer connection still cost the connect, about 0 when it opened in time, and `outer_connect_start` then sits near `dial_start`.

Since PLX-1584 each summary (`connect`, `firstEvent`, `appConnect`, `appFirstEvent`, `roundTrip`) adds `p99Ms` and `maxMs` beside `n`, `medianMs`, and `p95Ms`, which keep their meaning. Both are nearest rank, so with fewer than 100 samples p99 is the max. `metrics.samples.connects` keeps every counted dial in the order it ran, each with `dial`, `atMs` (its start, from the start of the stream check, before the warm-up), `connectMs`, and `firstEventMs`. With `--timings`, it adds `gap`, the largest difference between consecutive client markers named by the later one (the first, `main`, counts from spawn), and `relay`, the largest `Server-Timing` entry other than `worker` and `spare`. Relay entries overlap, so `relay` sits inside the `relay_upgrade_ready` gap, and `host_open` includes `admit` and `take`. Entry i is `metrics.stages[i]`, and a failed attempt's stage rows come last with no sample. `metrics.samples.roundTrips` keeps each round trip's `atMs`, on the same clock, and `ms`. Each connect prints one line as it runs, such as `relay 12/60 at 31.4 s: connect 1108 ms, first event 1109 ms, slowest relay_upgrade_ready 820 ms, relay stream_join 607 ms`, and the end lists the samples at or over each p95, in order, to the console and relay-probe.md. `t3-compare` keeps T3's samples the same way, with `atMs` from its first warm-up, and prints median, p95, p99, and max for connect, first event, and round trip on both. For the tail, pass `--connects 60 --trips 200`. Pass `--plxd <path>` to the probe, or to `t3-compare.mjs`, to time a plxd built here, and `--parallax-only` to `t3-compare.mjs` to skip T3. `t3-compare` sets T3's connect against `connect`, and prints `appConnect` on a line of its own.

`PLXD_CONNECT_TIMINGS=1` emits at most 64 fixed-name numeric stderr lines per process. Client `connect-timing` values are cumulative milliseconds from first instrumentation in main. Ordered differences locate CLI/runtime/credential setup, outer DNS/TCP/proxy, outer TLS configuration/handshake, authenticated relay upgrade, stream-ready wait, pinned TLS, inner WebSocket upgrade, and first inbound text frame. A first frame is usually initialize's response, not the first subscription event. The probe independently retains its first-event timer. Failed stages have no completion marker. Fallbacks/retries repeat stage names, so interpret in order, not as a map. `outer_tls_ready` on local HTTP means transport ready without TLS.

The probe records each stage's value and `observedMs` from the external spawn timer. The main marker's receipt is an upper bound for launch/loader time, including pipe scheduling, not an exact OS process creation timestamp. Other checkpoints also incur small stderr overhead. Do not use instrumented vs uninstrumented runs to claim small improvements.

Clients cannot split relay authentication from host object admission and spare selection. When opted in, they request `x-parallax-timing: 1`; a successful authenticated upgrade returns six numeric `Server-Timing` entries: `auth` (Clerk verification, including any JWKS fetch), `host_open` (host RPC including admission and selection), `stream_join` (stream-object client upgrade RPC), `admit`, `take` (inside host_open), and `spare` (1 or 0, a flag, not a duration). These overlap: do not sum host_open with admit/take. They use local durations, not synchronized clocks. Worker routing/rate-limit time before the handler, transit and scheduling remain in the client/server difference. No persisted logs or IDs are added. The client prints only allowlisted finite numeric entries in 0..60000 ms, within the same 64-line cap.

Since PLX-1493 the upgrade also returns `limit` (the anonymous rate limit's answer), `jwks` (the JWKS read, present only when this request made one), `host_hop` (a call to the host object that does nothing, made beside the stream's join) and `worker` (the request's start through the stream's 101). `limit` and `auth` both start with the request and run side by side, so they overlap, and the time before `host_open` is the longer of the two. `host_open` minus `host_hop` is the host object's own work, with its claim write's confirmation. The client's relay upgrade minus `worker` is one round trip plus what Cloudflare spends outside the Worker. Cloudflare's timers advance only after I/O, so a stage with no I/O reads 0: an `auth` of 0 means the isolate had the keys.

A manual run of the Relay probe workflow keeps each connect's stages in its artifact, from a GitHub runner, with no token on anyone's computer. Its `relay` input picks production or staging, and `connects` set to 30 gives enough samples to compare two runs. The older fields come from plxd's output, so they need no new plxd. The four new ones need a plxd from after PLX-1493 there, and until then the probe's object rows (`relay-objects.mjs`) carry them for its own timed streams, as `spare: relay limit` and the like.
